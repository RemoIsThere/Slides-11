02 · Foundations

What is a design pattern?

A design pattern is a reusable, named approach to a recurring software design problem.

It is

  • A design template or approach
  • A shared vocabulary for developers
  • A way to organize responsibilities

It is not

  • A complete application
  • A code snippet that fits every case
  • An algorithm for calculating an answer
Teach the problem first. A pattern is useful only when it makes the design clearer than the simpler alternative.
03 · Motivation

Why patterns are useful

01

Maintainability

Responsibilities are clearer, so changes are easier to localize.

02

Extensibility

New implementations can often be added without rewriting client logic.

03

Communication

“Use Observer” conveys a design idea faster than a long description.

Patterns add structure and classes. Do not use one merely to make a small program look sophisticated.
04 · Example problem

When code becomes hard to extend

class NotificationService {
    void send(String type, String message) {
        if (type.equals("EMAIL")) {
            System.out.println("Email: " + message);
        } else if (type.equals("SMS")) {
            System.out.println("SMS: " + message);
        }
    }
}
  • Every new notification type adds another branch.
  • The service knows the details of every channel.
  • Testing each behavior in isolation is harder.
This code is not automatically wrong. It becomes a design problem when types and rules keep growing.

08 · Creational

Singleton pattern

Ensure a class has one instance and provide a shared access point to it.

Typical structure

  • Private constructor
  • Static instance
  • Public access method

Possible use cases

  • Shared application configuration
  • A single process-level registry
  • Carefully designed shared service
Singletons introduce global state and can complicate tests. Use them only when a single shared instance is a genuine requirement.
09 · Singleton code

Java implementation

class CollegeConfig {
    private static final CollegeConfig INSTANCE =
            new CollegeConfig();

    private CollegeConfig() { }

    public static CollegeConfig getInstance() {
        return INSTANCE;
    }
}

class Main {
    public static void main(String[] args) {
        CollegeConfig a = CollegeConfig.getInstance();
        CollegeConfig b = CollegeConfig.getInstance();
        System.out.println(a == b); // true
    }
}
  • private blocks ordinary construction from outside.
  • static final holds one reference for this class loader.
  • The eager instance is created during class initialization.

11 · Creational

Factory Method pattern

Define a creation method; subclasses decide which concrete product to instantiate.

Creator
factory method
→
Product
interface

Roles

  • Product interface
  • Concrete products
  • Creator with factory method
  • Concrete creators

Example

A notification workflow works with Notification; an email creator supplies an email product and an SMS creator supplies an SMS product.

12 · Factory Method code

Notification factory

interface Notification {
    void send(String message);
}
class EmailNotification implements Notification {
    public void send(String m) {
        System.out.println("Email: " + m);
    }
}
abstract class Creator {
    abstract Notification createNotification();

    void notifyUser(String message) {
        createNotification().send(message);
    }
}
class EmailCreator extends Creator {
    Notification createNotification() {
        return new EmailNotification();
    }
}

Complete the example by adding SMSNotification and SMSCreator. Ask students which class decides the concrete product.

13 · Factory Method

Benefits and trade-offs

Benefits

  • Separates creation from use
  • Client code depends on an interface
  • Supports new product implementations

Trade-offs

  • May add several classes
  • Can be excessive for a tiny fixed set of objects
  • Creation responsibility must be placed sensibly
Class activity: Add a WhatsApp notification without changing the existing email product class.

Note: A simple static factory method is a related technique, but it is not automatically the GoF Factory Method pattern.

14 · Creational

Abstract Factory pattern

Provide an interface for creating families of related objects without naming their concrete classes.

GUIFactory
→
Button + Checkbox

Windows family

WindowsFactory creates WindowsButton and WindowsCheckbox.

Mac family

MacFactory creates MacButton and MacCheckbox.

The client chooses a factory family and receives products that belong together.
15 · Abstract Factory code

Build a matching product family

interface Button { void render(); }
interface Checkbox { void render(); }

class WindowsButton implements Button {
    public void render() { System.out.println("Windows button"); }
}
class WindowsCheckbox implements Checkbox {
    public void render() { System.out.println("Windows checkbox"); }
}

interface GUIFactory {
    Button createButton();
    Checkbox createCheckbox();
}
class WindowsFactory implements GUIFactory {
    public Button createButton() { return new WindowsButton(); }
    public Checkbox createCheckbox() { return new WindowsCheckbox(); }
}

Add a MacFactory that returns Mac products. Then write client code that depends only on GUIFactory.

16 · Factory comparison

Factory Method vs. Abstract Factory

PointFactory MethodAbstract Factory
Main goalCreate a product through a methodCreate a family of related products
Typical structureCreator and concrete creatorsFactory interface with multiple creation methods
ExampleEmail vs. SMS notificationWindows vs. Mac UI components
Extension pressureOften add a creator/product pairAdding a product family is easy; adding a new product kind can change every factory

17 · Structural

Bridge pattern

Separate an abstraction from its implementation so both can vary independently.

Abstraction hierarchy

Remote → AdvancedRemote

Represents the control features.

Implementation hierarchy

Device → TV, Radio

Represents the underlying device.

Remote
has a →
Device

Composition creates a bridge between the two hierarchies. A remote can work with different devices without a separate subclass for every combination.

18 · Bridge code

Remote and device

interface Device {
    void turnOn();
    void turnOff();
}
class TV implements Device {
    public void turnOn() { System.out.println("TV ON"); }
    public void turnOff() { System.out.println("TV OFF"); }
}
class Remote {
    protected final Device device;
    Remote(Device device) { this.device = device; }
    void powerOn() { device.turnOn(); }
    void powerOff() { device.turnOff(); }
}
class AdvancedRemote extends Remote {
    AdvancedRemote(Device device) { super(device); }
    void mute() { System.out.println("Muted"); }
}

Example use: new Remote(new TV()).powerOn();

Ask: What changes if a new Projector implements Device? The remote abstraction need not change.
19 · Bridge

Why use Bridge?

Without Bridge

Inheritance can multiply combinations: BasicTVRemote, AdvancedTVRemote, BasicRadioRemote, AdvancedRadioRemote…

With Bridge

Remote features and device types evolve separately. Composition connects the two.

  • Useful when two dimensions of variation exist.
  • Reduces subclass explosion.
  • Can add abstraction layers that are unnecessary in a very small system.
Practical: Add a Projector device and a new remote feature without changing existing device classes.
20 · Structural

Flyweight pattern

Share common object state to reduce the memory cost of many similar objects.

Intrinsic state

Shared, stable data kept in the flyweight: character symbol and font.

Extrinsic state

Context-specific data supplied from outside: position of a character on the page.

Think of a text editor displaying thousands of characters. Shared style objects can avoid storing identical formatting data repeatedly.
21 · Flyweight code

Cache and reuse objects

import java.util.*;

class CharacterStyle {
    private final char symbol;
    private final String font;

    CharacterStyle(char symbol, String font) {
        this.symbol = symbol;
        this.font = font;
    }
    void display(int position) {
        System.out.println(symbol + " " + font + " at " + position);
    }
}
class CharacterFactory {
    private static final Map CACHE =
        new HashMap<>();

    static CharacterStyle get(char c, String font) {
        String key = c + ":" + font;
        return CACHE.computeIfAbsent(
            key, k -> new CharacterStyle(c, font));
    }
}

Call get('A', "Arial") twice. Both calls return the same cached object for that key.

22 · Flyweight

Benefits and cautions

Benefits

  • Less duplicated shared state
  • Lower memory use at large scale
  • Centralized reuse through a factory

Cautions

  • Cache adds complexity
  • Shared state should generally be immutable
  • Cache growth may itself consume memory
  • Concurrent access needs thought
Practical: Design a tree renderer. Share tree type, texture, and color data; keep each tree's position outside the shared object.
23 · Behavioral

Iterator pattern

Traverse a collection without exposing how its elements are stored.

Java interfaces

Iterable<T> supplies an iterator. Iterator<T> traverses the elements.

Core methods

  • hasNext() — another element?
  • next() — return next element
  • remove() — optional operation
The same traversal style can work across different collection implementations.
24 · Iterator code

Use a Java iterator

import java.util.*;

class Main {
    public static void main(String[] args) {
        List students = new ArrayList<>();
        students.add("Aman");
        students.add("Riya");
        students.add("Karan");

        Iterator it = students.iterator();
        while (it.hasNext()) {
            System.out.println(it.next());
        }
    }
}

Output: Aman, Riya, Karan — each on a separate line.

  • iterator() obtains the traversal object.
  • next() advances the traversal.
  • Calling next() after exhaustion normally throws NoSuchElementException.
25 · Custom Iterator

Understand the mechanics

class StudentCollection implements Iterable {
    private final String[] data = {"Aman", "Riya", "Karan"};

    public Iterator iterator() {
        return new Iterator() {
            private int index = 0;

            public boolean hasNext() {
                return index < data.length;
            }

            public String next() {
                if (!hasNext()) throw new NoSuchElementException();
                return data[index++];
            }
        };
    }
}

Because the class implements Iterable, it can be used in an enhanced for loop.

Practical: Create a custom iterator for roll numbers and print only even values.
26 · Behavioral

Observer pattern

When a subject changes, it notifies its registered observers.

Subject
subscribe / notify
→
Observer A
+
Observer B

Subject

Maintains the subscriber list and sends updates.

Observer

Defines a method that each subscriber implements.

Example: A result publisher notifies subscribed students when results are announced.

27 · Observer code

Publish to subscribers

interface Observer {
    void update(String message);
}
class Student implements Observer {
    private final String name;
    Student(String name) { this.name = name; }
    public void update(String message) {
        System.out.println(name + ": " + message);
    }
}
class ResultPublisher {
    private final List observers = new ArrayList<>();

    void subscribe(Observer o) { observers.add(o); }
    void unsubscribe(Observer o) { observers.remove(o); }

    void publish(String message) {
        for (Observer o : observers) o.update(message);
    }
}

Register two students, publish an announcement, unsubscribe one, then publish again. Only the remaining subscriber receives the second update.

28 · Architecture

MVC: Model–View–Controller

MVC separates an application into three responsibilities.

Model

Data and domain rules. Example: student name and marks.

View

Presentation. Example: screen or report showing marks.

Controller

Handles input and coordinates model/view work.

User input
→
Controller
→
Model

The controller can then select or update the view. Real MVC frameworks differ in the exact request and update flow.

29 · MVC implementation

Small Java example

class Student {
    private final String name;
    private final int marks;
    Student(String name, int marks) {
        this.name = name; this.marks = marks;
    }
    String getName() { return name; }
    int getMarks() { return marks; }
}
class StudentView {
    void display(String name, int marks) {
        System.out.println(name + " — " + marks);
    }
}
class StudentController {
    private final Student model;
    private final StudentView view;
    StudentController(Student m, StudentView v) {
        model = m; view = v;
    }
    void display() {
        view.display(model.getName(), model.getMarks());
    }
}

In main, create a Student, a StudentView, and a StudentController; call controller.display().

Extension: Replace the console view with a Swing view while keeping the model independent of the GUI.
