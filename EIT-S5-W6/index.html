01

Abstraction

Abstraction is the discipline of exposing what something does and hiding how it does it. It is the conceptual foundation of ADTs, abstract classes, interfaces, and generics.

Abstraction

What Is Abstraction?

Definition

Abstraction is the process of reducing complexity by exposing only the essential features of an entity while hiding the implementation details. It lets a client interact with an idea rather than a mechanism.

Two Levels of Abstraction

  • Interface abstraction: the public contract — what a client can call.
  • Data abstraction: the values an object can take and the operations defined on them.

Everyday Example

When you drive a car, you use a steering wheel, pedals, and gear lever. You do not need to know how the engine's fuel injection works. The steering wheel is the interface; the engine is the implementation.

Why It Matters

  • Reduces cognitive load for clients.
  • Allows implementation to change without breaking callers.
  • Enables testing and substitution.
  • Supports layered system design.
Abstraction

Abstract Classes

Definition

An abstract class is a class declared with abstract that cannot be instantiated. It may contain abstract methods (no body) and concrete methods (with body).

abstract class Shape {
    String name;

    public Shape(String name) {
        this.name = name;
    }

    abstract double area();

    void describe() {
        System.out.println(name + ": area=" + area());
    }
}

Rules

  • Cannot be instantiated with new.
  • Can have constructors (called via super).
  • Can have fields, concrete methods, and abstract methods.
  • Subclasses must override all abstract methods or be abstract themselves.

When to Use

Use an abstract class when subclasses share state or when you want to provide a partial implementation that subclasses complete.

Abstraction

Interfaces

Definition

An interface is a pure contract — a set of method signatures that implementing classes must fulfill. It defines what a type can do, not how.

interface Drawable {
    void draw();

    // default method (Java 8+)
    default void highlight() {
        System.out.println("Highlighting...");
    }

    // static method
    static void describe() {
        System.out.println("A drawable object");
    }
}

Implementation

class Circle implements Drawable {
    @Override
    public void draw() {
        System.out.println("Drawing circle");
    }
}

When to Use

Use an interface when unrelated classes share a capability, or when you need multiple inheritance of type.

Interface Members

  • Abstract methods (implicitly public).
  • default methods (Java 8+).
  • static methods (Java 8+).
  • private helper methods (Java 9+).
  • Constants — public static final.

Choose Abstract Class When

  • Subclasses share fields or constructors.
  • You want to provide partial behaviour.
  • You are modelling an "is-a" hierarchy with common state.

Choose Interface When

  • Unrelated classes share a capability.
  • You need multiple inheritance of type.
  • You want to decouple the contract from any implementation.
02

ADT Foundations

Lecture 27. An abstract data type is defined by its values and operations — not by how those values are stored. This section formalizes that idea with concrete state, invariants, and abstraction functions.

ADT Foundations

What Is an Abstract Data Type?

Definition

An ADT is a mathematical model of a data type defined by:

  • The values it can take.
  • The operations defined on those values.

It says nothing about representation. A Stack is a LIFO collection, regardless of whether it is stored as an array or a linked list.

Classic ADT Examples

  • Stack, Queue, Deque
  • List, Set, Map
  • String / Text
  • Polynomial, Matrix

ADT vs Data Structure

ADTData Structure
Conceptual modelConcrete implementation
What operations existHow they are performed
SpecificationRepresentation
Client-facingInternal

Why Separate Them?

Because representation choices can change (array → tree) without disturbing the client's code, as long as the ADT's contract stays the same.

ADT Foundations

Concrete State and Representation

Concrete State

The actual fields that store the data inside an object. The concrete state is the representation chosen by the implementer.

public class IntStack {
    private int[] data;   // concrete state
    private int top;     // concrete state
}

Representation Variants

An ADT may have multiple valid representations. The choice affects performance, memory, and complexity — not the client's view.

  • Stack: fixed array, dynamic array, linked list.
  • Set: hash table, balanced tree, sorted array.
  • Text: char[], StringBuilder, rope.

Representation Choice Matters

RepresentationStrengthWeakness
ArrayFast indexingFixed size, slow insert
Linked listFast insert/deleteSlow indexing
Hash tableO(1) lookupNo ordering
Balanced treeOrdered, O(log n)More memory

Key Insight

The client should never depend on the representation. If they do, changing it becomes a breaking change.

ADT Foundations

The Abstraction Function

Definition

An abstraction function maps each concrete state to the abstract value it represents. It answers: "given this internal state, what abstract value does the client see?"

Formal Notation

AF: ConcreteState → AbstractValue

For example, for a Stack implemented as an array plus a top index:

AF(data, top) = data[0..top-1]

meaning: the abstract stack is the sequence of elements from index 0 through top-1.

Why It Matters

  • Precisely documents what the internal state means.
  • Guides implementers when writing methods.
  • Makes reasoning about correctness possible.
  • Exposes hidden assumptions early.

Example — Text ADT

A Text implemented as a StringBuilder might have:

AF(buffer) = buffer.toString()

Or for a gap-buffer representation:

AF(before, after) = before + reverse(after)
ADT Foundations

The Representation Invariant

Definition

A representation invariant is a condition that every valid concrete state must satisfy. It rules out states that do not correspond to any abstract value.

Example — IntStack

// Invariant:
//   0 <= top <= data.length
//   data[0..top-1] holds the elements
//   data[top..] is unused

If top > data.length or top < 0, the state is invalid and the abstraction function is undefined.

Why Invariants Matter

  • They define what "valid" means for the representation.
  • Every public method must preserve them.
  • Constructors must establish them.
  • They enable disciplined, bug-free design.

Enforcing Invariants

  • Keep fields private.
  • Validate inputs in constructors and setters.
  • Ensure every mutator leaves the invariant intact.
  • Use assertions in development to check invariants.

Text ADT — Invariant

// For a StringBuilder-backed Text:
//   buffer != null
//   buffer.length() == current length
ADT Foundations

Worked Example — The Text ADT

Abstract Value

A finite sequence of characters. Operations include: length(), charAt(i), append(c), insert(i, c), delete(i), substring(a,b), toString().

Representation Choice

Use a StringBuilder for efficient mutation.

public class Text {
    private StringBuilder buffer;

    // Abstraction function:
    //   AF(buffer) = buffer.toString()

    // Representation invariant:
    //   buffer != null
}

Implementation Sketch

public Text() {
    buffer = new StringBuilder();
}

public int length() {
    return buffer.length();
}

public char charAt(int i) {
    if (i < 0 || i >= buffer.length())
        throw new IndexOutOfBoundsException();
    return buffer.charAt(i);
}

public void append(char c) {
    buffer.append(c);
}

public void insert(int i, char c) {
    if (i < 0 || i > buffer.length())
        throw new IndexOutOfBoundsException();
    buffer.insert(i, c);
}

public void delete(int i) {
    if (i < 0 || i >= buffer.length())
        throw new IndexOutOfBoundsException();
    buffer.deleteCharAt(i);
}

@Override
public String toString() {
    return buffer.toString();
}
ADT Foundations

ADT Decomposition & Abstraction

Procedural Abstraction

Hides the steps of a computation behind a named procedure.

double area = circleArea(5);

static double circleArea(double r) {
    return Math.PI * r * r;
}

Data Abstraction

Hides the representation of a value behind an interface of operations.

class Stack<T> {
    void push(T x) { ... }
    T pop() { ... }
}

Type Abstraction

Hides the identity of types behind type parameters — the essence of generics.

class Box<T> {
    T value;
}

Progression

Procedural abstraction is about operations; data abstraction is about representation; type abstraction is about types. Generics sit at the third level.

ADT Foundations

Parameterization and Specification

Parameterization

Making an ADT work over an arbitrary type rather than a fixed one. Instead of IntStack, we write Stack<T>.

class Stack<T> {
    private List<T> items = new ArrayList<>();
    void push(T item) { items.add(item); }
    T pop() { return items.remove(items.size() - 1); }
    boolean isEmpty() { return items.isEmpty(); }
}

Specification

A specification describes what an operation does — preconditions, postconditions, and invariants — without prescribing implementation.

// push(x)
// Precondition:  none
// Postcondition: top becomes x;
//                size increases by 1
// Invariant:     size >= 0

Specification vs Implementation

A good specification tells the caller everything they need and nothing about how it is done. This is what lets the implementation evolve.

03

Generics

Lectures 28–29. Generics let you write classes, interfaces, and methods that are parameterized over types — giving you the type safety of specific code with the reusability of general code.

Generics

Simple Generics

Before Generics — The Problem

List list = new ArrayList();
list.add("Hello");
list.add(42);       // no type check

String s = (String) list.get(1);
// ClassCastException at runtime

You must cast, and errors appear only at runtime.

With Generics — The Solution

List<String> list = new ArrayList<>();
list.add("Hello");
// list.add(42); // compile error

String s = list.get(0); // no cast

Errors appear at compile time; casts are inserted automatically.

Benefits

  • Compile-time type safety.
  • No explicit casts.
  • Clear intent in the type signature.
  • Reusable across many element types.
Generics

Generic Classes

Syntax

class ClassName<T> {
    // T is a type parameter
}

Conventionally, type parameters use single uppercase letters: T (type), E (element), K (key), V (value), R (result).

Usage

Box<String> b1 = new Box<>("Hello");
Box<Integer> b2 = new Box<>(42);

String s = b1.getValue();   // String
int n = b2.getValue();      // Integer

Example — Box

public class Box<T> {
    private T value;

    public Box(T value) {
        this.value = value;
    }

    public T getValue() {
        return value;
    }

    public void setValue(T value) {
        this.value = value;
    }

    @Override
    public String toString() {
        return "Box[" + value + "]";
    }
}

Multiple Type Parameters

class Pair<K, V> {
    private K key;
    private V value;
}
Generics

Generic Interfaces

Definition

interface Pair<K, V> {
    K getKey();
    V getValue();
}

Implementation

public class OrderedPair<K, V>
        implements Pair<K, V> {

    private K key;
    private V value;

    public OrderedPair(K key, V value) {
        this.key = key;
        this.value = value;
    }

    @Override
    public K getKey() { return key; }

    @Override
    public V getValue() { return value; }
}

Usage

Pair<String, Integer> p =
    new OrderedPair<>("age", 25);

System.out.println(p.getKey());   // age
System.out.println(p.getValue()); // 25

Non-Generic Implementation

A class may implement a generic interface with concrete types:

class StringIntPair
        implements Pair<String, Integer> {
    // ...
}

Reusable Type-Safe Components

Generic interfaces are the backbone of reusable APIs — the client chooses the type, the interface guarantees the contract.

Generics

Generic Methods

Syntax

public static <T> ReturnType methodName(T arg) { ... }

The type parameter is declared before the return type, independent of any class-level type parameter.

Example — printArray

public static <T> void printArray(T[] array) {
    for (T element : array) {
        System.out.print(element + " ");
    }
    System.out.println();
}
Integer[] nums = {1, 2, 3};
String[] names = {"Alice", "Bob"};

printArray(nums);   // 1 2 3
printArray(names);  // Alice Bob

Example — swap

public static <T> void swap(T[] arr,
                              int i, int j) {
    T temp = arr[i];
    arr[i] = arr[j];
    arr[j] = temp;
}

Type Inference

Java usually infers the type parameter from the arguments. You rarely need to specify it explicitly.

Util.<Integer>printArray(nums); // explicit (rare)
printArray(nums);                // inferred (usual)
Generics

Bounded Type Parameters

Definition

You can restrict the types that a type parameter accepts using the extends keyword (for classes and interfaces).

<T extends Number>
<T extends Comparable<T>>
<T extends Number & Comparable<T>>

Example — NumberBox

public class NumberBox<T extends Number> {
    private T value;

    public NumberBox(T value) {
        this.value = value;
    }

    public double doubleValue() {
        return value.doubleValue();
    }
}
NumberBox<Integer> ib = new NumberBox<>(42);
NumberBox<Double> db = new NumberBox<>(3.14);
// NumberBox<String> sb = ...; // compile error

Example — Generic max

public static <T extends Comparable<T>>
T max(T a, T b) {
    return (a.compareTo(b) > 0) ? a : b;
}

max(10, 20);                 // 20
max("Apple", "Banana");      // Banana

Why Bound?

Without a bound, T is treated as Object, and you cannot call methods like doubleValue() or compareTo(). The bound exposes the needed API.

Generics

Wildcards

Three Forms

WildcardMeaning
?Any type
? extends TT or a subtype (upper bound)
? super TT or a supertype (lower bound)

Example — Upper Bound

public static double sumOfList(
        List<? extends Number> list) {
    double sum = 0;
    for (Number n : list) {
        sum += n.doubleValue();
    }
    return sum;
}
List<Integer> ints = List.of(1, 2, 3);
List<Double> dbls = List.of(1.5, 2.5);

sumOfList(ints);   // 6.0
sumOfList(dbls);   // 4.0

PECS Principle

Producer Extends, Consumer Super.

  • If you only read from a structure: ? extends T.
  • If you only write to it: ? super T.
  • If you do both: no wildcard.

Lower Bound Example

public static void addInts(
        List<? super Integer> list) {
    list.add(42);   // safe to write
    // Integer x = list.get(0); // not safe to read
}

Unbounded Wildcard

public static void printAll(List<?> list) {
    for (Object o : list) {
        System.out.println(o);
    }
}
Generics

Generic Subtyping

The Surprising Rule

List<Integer> is not a subtype of List<Number>, even though Integer is a subtype of Number.

List<Integer> ints = new ArrayList<>();
// List<Number> nums = ints; // compile error

Why?

If the assignment were allowed, you could add a Double to the list via the List<Number> reference, corrupting the original List<Integer>.

nums.add(3.14); // would corrupt ints
Integer i = ints.get(0); // ClassCastException

The Correct Relationship

With wildcards, you can express covariance and contravariance:

List<Integer> ints = new ArrayList<>();

// Covariant read-only view
List<? extends Number> readOnly = ints;

// Contravariant write-only view
List<? super Integer> writeOnly = ints;

Subtyping Rules Summary

FromToAllowed?
List<Integer>List<?>Yes
List<Integer>List<? extends Number>Yes
List<Integer>List<? super Integer>Yes
List<Integer>List<Number>No
Generics

Type Erasure

Definition

Java implements generics through type erasure: the compiler removes all type parameters and inserts casts where necessary. At runtime, generic type information is gone.

List<String> list = new ArrayList<>();
// At runtime this is just ArrayList

Consequences

  • Cannot use instanceof with parameterized types.
  • Cannot create arrays of generic types.
  • Cannot overload methods that differ only in type parameters.
  • Cannot call new T() or T.class.

Compile Errors

// if (list instanceof List<String>) { }
// T[] arr = new T[10];
// void m(List<String> l) { }
// void m(List<Integer> l) { } // same erasure

Why Type Erasure?

It preserved backward compatibility with pre-generics code. The JVM never had to change its bytecode format — generics are a compile-time feature.

Workaround — Class Token

public static <T> T create(
        Class<T> clazz) throws Exception {
    return clazz.getDeclaredConstructor().newInstance();
}

Generic Practical

Generic Pair

Implementation

public class Pair<A, B> {
    private final A first;
    private final B second;

    public Pair(A first, B second) {
        this.first = first;
        this.second = second;
    }

    public A getFirst() { return first; }
    public B getSecond() { return second; }

    // Factory method
    public static <X, Y> Pair<X, Y> of(X x, Y y) {
        return new Pair<>(x, y);
    }

    @Override
    public String toString() {
        return "(" + first + ", " + second + ")";
    }
}

Usage

Pair<String, Integer> p1 =
    Pair.of("age", 25);

Pair<Double, Boolean> p2 =
    Pair.of(3.14, true);

System.out.println(p1); // (age, 25)
System.out.println(p2); // (3.14, true)

Design Notes

  • Fields are final — a Pair is immutable.
  • Factory method of avoids the new noise.
  • The type parameters A and B are independent.
Generic Practical

Generic Stack

Implementation

import java.util.ArrayList;
import java.util.List;
import java.util.EmptyStackException;

public class Stack<T> {
    private List<T> items = new ArrayList<>();

    public void push(T item) {
        items.add(item);
    }

    public T pop() {
        if (items.isEmpty())
            throw new EmptyStackException();
        return items.remove(items.size() - 1);
    }

    public T peek() {
        if (items.isEmpty())
            throw new EmptyStackException();
        return items.get(items.size() - 1);
    }

    public boolean isEmpty() {
        return items.isEmpty();
    }

    public int size() {
        return items.size();
    }
}

Usage

Stack<Integer> s = new Stack<>();
s.push(10);
s.push(20);
s.push(30);

System.out.println(s.pop());   // 30
System.out.println(s.peek());  // 20
System.out.println(s.size());  // 2

ADT Perspective

  • Abstract value: a LIFO sequence of items.
  • Abstraction function: AF(items) = the sequence of elements.
  • Invariant: items != null.
  • Client only sees push, pop, peek, isEmpty, size.

Generic Utility Methods

max

public static <T extends Comparable<T>>
T max(T a, T b) {
    return (a.compareTo(b) > 0) ? a : b;
}

min

public static <T extends Comparable<T>>
T min(T a, T b) {
    return (a.compareTo(b) < 0) ? a : b;
}

filter

public static <T> List<T> filter(
        List<T> list,
        Predicate<T> predicate) {
    List<T> result = new ArrayList<>();
    for (T item : list) {
        if (predicate.test(item))
            result.add(item);
    }
    return result;
}

map

public static <T, R> List<R> map(
        List<T> list,
        Function<T, R> mapper) {
    List<R> result = new ArrayList<>();
    for (T item : list) {
        result.add(mapper.apply(item));
    }
    return result;
}

Usage

List<Integer> nums = List.of(1, 2, 3, 4, 5);

List<Integer> evens = filter(nums, n -> n % 2 == 0);
List<String> strs = map(nums, n -> "#" + n);

System.out.println(evens); // [2, 4]
System.out.println(strs);  // [#1, #2, #3, #4, #5]

Design Notes

Notice how <T> and <T, R> are declared on the method, not on a class. These are standalone, reusable building blocks.

Pattern

Notice the PECS pattern in every example:

  • Reading → extends.
  • Writing → super.
  • Doing both → plain T.
Generic Practical

Generic Repository Interface

Interface

public interface Repository<T, ID> {
    void save(T entity);
    Optional<T> findById(ID id);
    List<T> findAll();
    boolean deleteById(ID id);
    long count();
}

Implementation

public class InMemoryRepository<T, ID>
        implements Repository<T, ID> {

    private final Map<ID, T> store =
        new HashMap<>();
    private final Function<T, ID> idExtractor;

    public InMemoryRepository(
            Function<T, ID> idExtractor) {
        this.idExtractor = idExtractor;
    }

    @Override
    public void save(T entity) {
        store.put(idExtractor.apply(entity), entity);
    }

    @Override
    public Optional<T> findById(ID id) {
        return Optional.ofNullable(store.get(id));
    }

    @Override
    public List<T> findAll() {
        return new ArrayList<>(store.values());
    }

    @Override
    public boolean deleteById(ID id) {
        return store.remove(id) != null;
    }

    @Override
    public long count() {
        return store.size();
    }
}
Generic Practical

Repository Usage

Domain Classes

class Student {
    final int id;
    final String name;

    Student(int id, String name) {
        this.id = id;
        this.name = name;
    }

    int getId() { return id; }

    @Override
    public String toString() {
        return id + ":" + name;
    }
}

Usage

Repository<Student, Integer> repo =
    new InMemoryRepository<>(Student::getId);

repo.save(new Student(1, "Alice"));
repo.save(new Student(2, "Bob"));

repo.findById(1).ifPresent(System.out::println);
// 1:Alice

System.out.println(repo.count()); // 2

repo.findAll().forEach(System.out::println);
// 1:Alice
// 2:Bob

Design Points

  • Generic over T (entity) and ID (identifier).
  • Uses Optional to avoid returning null.
  • Uses Function<T, ID> to extract the identifier.
  • One implementation works for any entity type.

Common Operations

List<String> list = new ArrayList<>();

list.add("Alice");

System.out.println(list.contains("Alice")); // false

Rule of Thumb

Prefer ArrayList unless you need frequent insertion or removal at the front of a large list.

Set — HashSet and TreeSet

Set Characteristics

  • No duplicates.
  • No index-based access.
  • Order depends on implementation.

HashSet Example

Set<String> set = new HashSet<>();
set.add("Java");
set.add("Python");
set.add("Java");   // ignored (duplicate)

System.out.println(set.size());       // 2
System.out.println(set.contains("Java")); // true

TreeSet Example

Set<Integer> sorted = new TreeSet<>();
sorted.add(30);
sorted.add(10);
sorted.add(20);

System.out.println(sorted); // [10, 20, 30]

Key Reminder

For HashSet to work correctly, elements must override both equals() and hashCode().

Collections Framework

Queue, Deque and PriorityQueue

Queue (FIFO)

Queue<String> queue = new LinkedList<>();
queue.offer("A");
queue.offer("B");
queue.offer("C");

System.out.println(queue.poll()); // A
System.out.println(queue.peek()); // B

Deque (Double-Ended)

Deque<String> deque = new ArrayDeque<>();
deque.addFirst("B");
deque.addFirst("A");
deque.addLast("C");

System.out.println(deque); // [A, B, C]

deque.removeFirst();       // A
deque.removeLast();        // C

PriorityQueue

A queue where elements are dequeued according to priority rather than insertion order. Uses natural ordering or a Comparator.

PriorityQueue<Integer> pq = new PriorityQueue<>();
pq.offer(30);
pq.offer(10);
pq.offer(20);

while (!pq.isEmpty()) {
    System.out.println(pq.poll());
}
// 10
// 20
// 30

ArrayDeque

Prefer ArrayDeque over LinkedList for stack and queue use — it is faster and uses less memory.

Map — HashMap and LinkedHashMap

Map Characteristics

  • Stores key-value pairs.
  • Keys are unique.
  • Not part of the Collection hierarchy.

HashMap Example

Map<String, Integer> ages = new HashMap<>();
ages.put("Alice", 25);
ages.put("Bob", 30);
ages.put("Alice", 26); // overwrites

System.out.println(ages.get("Alice")); // 26
System.out.println(ages.containsKey("Bob")); // true
System.out.println(ages.size()); // 2

Iterating a Map

for (Map.Entry<String, Integer> e : ages.entrySet()) {
    System.out.println(e.getKey() + " → " + e.getValue());
}

// Or with forEach (Java 8+)
ages.forEach((k, v) -> System.out.println(k + " → " + v));

Collections Framework

Iteration

Enhanced For-Loop

The preferred way to iterate when you do not need to remove elements.

List<String> names = List.of("Alice", "Bob");

for (String name : names) {
    System.out.println(name);
}

Explicit Iterator

Required when you need to remove elements during iteration.

Iterator<String> it = names.iterator();
while (it.hasNext()) {
    String name = it.next();
    if (name.startsWith("A")) {
        it.remove();  // safe removal
    }
}

Concurrent Modification

// BAD
for (String name : names) {
    if (name.equals("Bob")) {
        names.remove(name); // ConcurrentModificationException
    }
}

Modifying a collection structurally while iterating with a for-each throws this exception.

forEach Method (Java 8+)

names.forEach(System.out::println);

ages.forEach((k, v) ->
    System.out.println(k + ": " + v));
Collections Framework

Object Ordering — Comparable & Comparator

Comparable<T> — Natural Ordering

Implemented by the class itself. Defines the "natural" ordering of its instances.

public class Student
        implements Comparable<Student> {

    private int rollNo;
    private String name;

    @Override
    public int compareTo(Student other) {
        return Integer.compare(
            this.rollNo, other.rollNo);
    }
}
List<Student> students = new ArrayList<>();
// ... add students ...
Collections.sort(students); // uses compareTo

Comparator<T> — Custom Ordering

A separate object that defines an ordering. Useful when you need multiple orderings, or the class is not under your control.

Comparator<Student> byName =
    (s1, s2) -> s1.getName().compareTo(s2.getName());

Comparator<Student> byGpaDesc =
    Comparator.comparingDouble(Student::getGpa)
              .reversed();

students.sort(byName);
students.sort(byGpaDesc);

Choosing

  • Use Comparable for a single, obvious natural order.
  • Use Comparator for alternate or context-specific orderings.
  • TreeSet and TreeMap need one of the two.
Collections Framework

SortedSet and SortedMap

SortedSet

A Set that maintains its elements in sorted order. Implemented by TreeSet.

SortedSet<Integer> set = new TreeSet<>();
set.add(30);
set.add(10);
set.add(20);

System.out.println(set.first()); // 10
System.out.println(set.last());  // 30
System.out.println(set.headSet(20)); // [10]
System.out.println(set.tailSet(20)); // [20, 30]

SortedMap

A Map that maintains its keys in sorted order. Implemented by TreeMap.

SortedMap<String, Integer> map = new TreeMap<>();
map.put("Charlie", 3);
map.put("Alice", 1);
map.put("Bob", 2);

System.out.println(map.firstKey());  // Alice
System.out.println(map.lastKey());   // Charlie
System.out.println(map.headMap("Charlie"));
// {Alice=1, Bob=2}

Typical Use Cases

  • Leaderboards and rankings.
  • Range queries (e.g., dates in a window).
  • Ordered iteration of keys.
Wrap-Up

Summary and Checklist

Key Takeaways

  • Abstraction hides implementation and exposes contract.
  • Abstract classes share state and partial behaviour; interfaces define capabilities and support multiple inheritance of type.
  • An ADT is defined by values and operations, not representation.
  • Every representation has an abstraction function and a representation invariant.
  • Generics give compile-time type safety and code reuse.
  • Bounded type parameters restrict what types a parameter accepts.
  • Wildcards express covariance (extends) and contravariance (super).
  • Type erasure removes generic information at runtime.
  • The Collections Framework provides ready-made ADTs with different performance trade-offs.
  • Comparable is natural ordering; Comparator is external ordering.

Before Next Week, Ensure You Can

  • Write an abstract class and an interface, and choose between them.
  • Document the invariant and abstraction function for a small ADT.
  • Write a generic class, interface, and method.
  • Apply bounded type parameters to enforce API contracts.
  • Use ? extends T and ? super T correctly.
  • Implement a generic repository backed by a Map.
  • Choose the right collection for a task (List / Set / Queue / Map).
  • Iterate safely, avoiding ConcurrentModificationException.
  • Order objects with Comparable and Comparator.
