01

String Handling

Text is everywhere. Java gives us two primary tools for it: the immutable String and the mutable StringBuilder. Knowing when to use which is a mark of a competent Java programmer.

String Handling

The String Class

What is a String?

A String is an object that represents a sequence of characters. It is not a primitive type — it is a reference type defined in java.lang.

Two Ways to Create

// 1. String literal (goes to the string pool)
String a = "Hello";

// 2. Using the constructor (new object on the heap)
String b = new String("Hello");

The String Pool

String literals are stored in a special memory region called the string pool. If two literals have the same content, they point to the same object.

String s1 = "Java";
String s2 = "Java";
System.out.println(s1 == s2); // true

String s3 = new String("Java");
System.out.println(s1 == s3); // false

Key idea: == compares references; equals() compares content. For strings, use equals().

String Handling

String Immutability

What Does Immutable Mean?

Once a String object is created, its contents cannot be changed. Any operation that appears to modify a string actually creates a new String object.

Demonstration

String s = "Hello";
s = s + " World";
System.out.println(s); // Hello World

The original "Hello" object is untouched. s now points to a new object "Hello World".

Why Is It Designed This Way?

  • Security: Strings are used in file paths, network connections, and class loading. Immutability prevents tampering.
  • Caching: Hash codes can be cached because the value never changes.
  • Thread safety: Immutable objects can be shared freely between threads.
  • String pool: Reusing literals only works if they can't be mutated.

Consequence: Concatenating inside a loop creates a new object every iteration — use StringBuilder instead.

String Handling

Comparing Strings: == vs equals()

== — Reference Comparison

Checks whether two variables point to the same object in memory.

String a = "Java";
String b = "Java";
String c = new String("Java");

a == b  // true  (same pool object)
a == c  // false (different objects)

equals() — Content Comparison

Checks whether two strings contain the same characters.

a.equals(b)  // true
a.equals(c)  // true

Rule of Thumb

Always use equals() (or equalsIgnoreCase()) to compare string content. Reserve == for primitives and for deliberate reference-identity checks.

Common Bug

if (userInput == "yes") { ... }
// Fails when input comes from Scanner or new String()

// Correct:
if (userInput.equals("yes")) { ... }
String Handling

StringBuilder — Introduction

What Is It?

StringBuilder is a mutable sequence of characters. Unlike String, its contents can be changed in place without creating a new object each time.

Creating a StringBuilder

StringBuilder sb = new StringBuilder();
StringBuilder sb2 = new StringBuilder("Start");
StringBuilder sb3 = new StringBuilder(50); // capacity

Why Capacity Matters

Default capacity is 16 characters. When exceeded, the internal array is reallocated. Pre-sizing avoids repeated reallocation in hot loops.

The Classic Loop Problem

// BAD: creates ~n new String objects
String result = "";
for (int i = 0; i < 1000; i++) {
    result += i;
}

// GOOD: mutates one object
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 1000; i++) {
    sb.append(i);
}
String result2 = sb.toString();

Wrapper Classes

Primitives are fast but limited. Wrapper classes give them object identity, methods, and the ability to participate in collections — at the cost of a little overhead.

Wrapper Classes

Primitive vs Wrapper Types

Primitive Types

  • Eight types: byte, short, int, long, float, double, char, boolean.
  • Store the value directly.
  • No methods, no null.
  • Fast and memory-efficient.
  • Cannot be used in generic collections.

Wrapper Types

  • Classes in java.lang: Integer, Double, Character, Boolean, etc.
  • Hold a primitive value inside an object.
  • Provide utility methods (parsing, conversion, comparison).
  • Can be null — useful and dangerous.
  • Required by collections and generics.

Why Wrappers Exist

Java's collections (ArrayList, HashMap, …) work only with objects. Generics cannot be parameterized by primitives. Wrappers bridge that gap.

ArrayList<Integer> scores = new ArrayList<>();
scores.add(95); // autoboxed to Integer

Wrapper Classes

Autoboxing and Unboxing

Autoboxing

Automatic conversion of a primitive to its wrapper object.

Integer i = 42;
// compiler inserts: Integer.valueOf(42)

Unboxing

Automatic conversion of a wrapper object back to a primitive.

Integer i = 42;
int x = i;
// compiler inserts: i.intValue()

NullPointerException Hazard

Integer count = null;
int n = count; // NullPointerException at runtime

Unboxing a null wrapper throws immediately. Always guard against null when unboxing.

Equality Trap

Integer a = 1000;
Integer b = 1000;
System.out.println(a == b);      // false
System.out.println(a.equals(b)); // true

Small values (−128..127) are cached, so == may accidentally work. Do not rely on it — use equals().

Wrapper Classes

Wrapper Class Utility Methods

Parsing Strings → Primitives

int n = Integer.parseInt("123");
double d = Double.parseDouble("3.14");
boolean b = Boolean.parseBoolean("true");

Throws NumberFormatException if the string is not a valid number.

Converting to String

String s1 = Integer.toString(42);
String s2 = String.valueOf(3.14);
String s3 = "" + 42; // implicit

Comparison

Integer a = 10, b = 20;
a.compareTo(b); // negative
Integer.compare(a, b); // -1

Character Utilities

Character.isLetter('A');   // true
Character.isDigit('7');    // true
Character.isWhitespace(' '); // true
Character.toUpperCase('a'); // 'A'

Bounds

Integer.MAX_VALUE // 2147483647
Integer.MIN_VALUE // -2147483648
Double.MAX_VALUE  // 1.7976931348623157E308
03

Varargs

Sometimes a method should accept any number of arguments. Varargs let you write sum(1, 2, 3, 4) without overloading the method four times.

Varargs

Variable-Length Arguments — Syntax

Syntax

returnType methodName(Type... name) {
    // name is treated as Type[]
}

The three dots ... are the varargs operator. Inside the method, the parameter behaves exactly like an array.

Simple Example

public static int sum(int... nums) {
    int total = 0;
    for (int n : nums) {
        total += n;
    }
    return total;
}

sum();              // 0
sum(1, 2);          // 3
sum(1, 2, 3, 4, 5); // 15

Mixing Fixed and Varargs

public static void log(String level, String... messages) {
    for (String m : messages) {
        System.out.println("[" + level + "] " + m);
    }
}

log("INFO", "Started", "Loaded");
log("WARN"); // zero varargs — valid

Passing an Array

int[] data = {1, 2, 3};
sum(data); // works — array is accepted directly
Varargs

Varargs — Rules and Use Cases

Rules

  • Only one varargs parameter per method.
  • It must be the last parameter.
  • It is implemented as an array — nums.length works.
  • The method can be called with zero arguments.
  • Overloading with varargs can create ambiguity — use with care.

Invalid

// Two varargs — compile error
void bad(int... a, String... b) { }

// Varargs not last — compile error
void bad2(int... a, String s) { }

Good Use Cases

  • Utility methods: sum, max, min, join.
  • Logging helpers with variable message counts.
  • Formatting helpers: String.format(fmt, args...).
  • Builder-style APIs that accept optional extras.

Avoid When

  • The number of arguments is fixed.
  • Type safety would be weakened (prefer generics).
  • Overload resolution becomes confusing.

Standard Library Example

System.out.printf("%s scored %d%n", name, score);
// printf(String format, Object... args)
04

Packages & Imports

As projects grow, names collide and files multiply. Packages provide namespace management, access control, and a sane directory structure.

Packages

Why Packages Exist

Organization

Groups related classes together. A large project with 500 classes becomes navigable when split into logical packages.

Naming Conflicts

Two teams can both define a Date class if they live in different packages: com.a.Date and com.b.Date.

Access Control

Package-private (default) members are visible only within the same package — a powerful encapsulation tool.

Reusability

Packages can be compiled into JAR files and reused across projects.

Maintainability

Clear boundaries make refactoring and testing easier.

Security

Package boundaries interact with the class loader and security manager.

Without packages: every class competes for a single global namespace. With a few hundred classes, collisions become inevitable.

Packages

Creating and Using a Package

Step 1 — Declare the Package

The package statement must be the first line of the source file (comments aside).

// File: com/example/shapes/Circle.java
package com.example.shapes;

public class Circle {
    public double area(double r) {
        return Math.PI * r * r;
    }
}

Step 2 — Match the Directory

The folder structure must mirror the package name:

src/
 └── com/
     └── example/
         └── shapes/
             └── Circle.java

Step 3 — Compile

javac -d out src/com/example/shapes/Circle.java
# -d out places .class files under out/com/example/shapes/

Step 4 — Run

java -cp out com.example.shapes.Circle

Note the fully qualified class name: package.ClassName.

Rule

One package declaration per file. No package declaration means the class lives in the default package — acceptable for tiny demos, bad for real code.

Packages

Import Statements

Single-Class Import

import java.util.Scanner;
import java.util.ArrayList;

Imports exactly one class. Preferred — makes dependencies explicit.

On-Demand (Wildcard) Import

import java.util.*;

Imports all classes in the package. Does not import sub-packages.

Static Import

import static java.lang.Math.PI;
import static java.lang.Math.sqrt;

double a = PI * sqrt(2);

Brings static members into scope without the class prefix. Use sparingly.

Implicit Import

Every compilation unit automatically imports java.lang.*. That is why String, System, and Math work without an import.

Name Collision

import java.util.Date;
import java.sql.Date; // compile error

Resolve with fully qualified names or import only one.

Packages

Package Organization and Naming

Naming Convention

Use the reverse domain name to guarantee global uniqueness:

com.company.project.module
org.opensource.library

All lowercase. No underscores or hyphens. Dots separate levels.

Common Layering

com.example.app
├── model        // data classes
├── service      // business logic
├── repository   // persistence
├── controller   // entry points
└── util         // helpers

Build Tool Layout (Maven/Gradle)

src/
 ├── main/
 │   └── java/
 │       └── com/example/app/...
 └── test/
     └── java/
         └── com/example/app/...

Practical Advice

  • Do not create deep hierarchies "just in case".
  • Prefer feature-based packages over type-based ones as projects grow.
  • Keep the default package empty in production code.
  • Package-private access is a design tool — use it intentionally.

Access Modifiers

Encapsulation begins with a simple question: who is allowed to see and change this? Java answers with four levels of access.

Access Control

The Four Access Levels

public

Visible to everyone, from any package.

Use for API entry points.

protected

Visible within the package and to subclasses in other packages.

Use for inheritance-friendly members.

default

No modifier. Visible only within the same package.

Package-private; a strong encapsulation tool.

private

Visible only within the same class. The most restrictive level.

Use for internal state and helper methods.

Where They Apply

  • Classes (only public or default)
  • Fields
  • Methods
  • Constructors
  • Nested classes and interfaces
Access Control

public and private

public

No restrictions. Accessible from any class, any package, any subclass.

public class Calculator {
    public int add(int a, int b) {
        return a + b;
    }
}

Use for the contract you are offering to other code.

private

Accessible only inside the same class. Not visible to subclasses either.

public class BankAccount {
    private double balance;

    public void deposit(double amt) {
        if (amt > 0) balance += amt;
    }

    public double getBalance() {
        return balance;
    }
}

Principle: make fields private by default, expose behaviour through public methods. This is encapsulation.

Access Control

protected and default

protected

Same-package access plus access from subclasses in other packages.

package com.example.shapes;

public class Shape {
    protected double area;
}

// In another package:
public class Circle extends Shape {
    void compute() {
        area = 3.14; // allowed via inheritance
    }
}

protected is designed for inheritance. It is not "public but nicer".

default (Package-Private)

No modifier written. Visible only within the same package.

package com.example.util;

class InternalHelper {   // default class
    void run() { ... }    // default method
}

Useful for internal collaboration without exposing a public API.

Practical Guidance

  • Start with the most restrictive level that works.
  • Widen only when a real need appears.
  • Most fields: private.
  • Most public API methods: public.
  • Inheritance hooks: protected.
Access Control

Access Control — Full Comparison

Modifier Same Class Same Package Subclass (other package) Anywhere
publicYesYesYesYes
protectedYesYesYesNo
defaultYesYesNoNo
privateYesNoNoNo

Why Access Control Matters

  • Encapsulation: hides internal representation.
  • Invariants: prevents invalid state changes.
  • Evolvability: internal changes don't break clients.
  • Security: limits the attack surface.
  • Clarity: communicates design intent.

Rule of Thumb

Design classes as if every member will be read by a stranger. Expose the minimum surface necessary. The narrower the access, the freer you are to change the implementation later.

06

Debugging Fundamentals

Errors are not failures. They are information. A disciplined debugging workflow turns a cryptic message into a specific fix.

Debugging

Three Categories of Errors

Compile-Time Errors

Detected by javac. The program does not compile.

int x = "hello";
// incompatible types
  • Syntax errors
  • Type mismatches
  • Missing imports
  • Undeclared variables

Runtime Errors

Occur while the program is running. Throw an exception.

int x = 10 / 0;
// ArithmeticException
  • NullPointerException
  • ArrayIndexOutOfBoundsException
  • NumberFormatException
  • InputMismatchException

Logical Errors

The program compiles and runs, but produces the wrong result.

// Intended: average of two numbers
double avg = a + b / 2;
// Precedence bug — should be (a + b) / 2
  • Wrong operator precedence
  • Off-by-one in loops
  • Wrong variable used
  • Misunderstood requirements

Compile-time errors are the easiest to fix because the compiler tells you the file and line. Logical errors are the hardest because nothing complains — you must reason about intent.

Debugging

A Disciplined Debugging Workflow

Step 1 — Read the Message Carefully

The compiler or JVM gives you a file name, a line number, and a specific complaint. Read it before changing anything.

Main.java:7: error: incompatible types
  int x = "hello";
        ^
  required: int  found: String

Step 2 — Locate the Exact Line

Go to the reported line. If the error mentions a symbol, search for where it is declared and where it is used.

Step 3 — Form a Hypothesis

State in one sentence what you believe is wrong. This prevents random edits and shotgun debugging.

Step 4 — Test the Hypothesis

Add a print statement, simplify the code, or comment out sections. Confirm or reject your belief before fixing.

System.out.println("x = " + x);
System.out.println("arr length = " + arr.length);

Step 5 — Fix and Re-run

Change one thing at a time. Re-run the program. If the symptom persists, your hypothesis was incomplete — return to Step 1.

Step 6 — Document and Prevent

Add a test, a comment, or a validation check so the same class of bug cannot silently return.

Tools

Print statements, IDE debugger with breakpoints, stack traces, assertions, and unit tests.

Object-Oriented Thinking

The bridge. Everything so far has lived inside main(). Now we move behaviour and data into classes that model the problem domain.

OOP Thinking

What Is a Class?

Definition

A class is a blueprint or template that defines the structure and behaviour of a category of objects. It specifies what data an object will hold and what operations it can perform.

Anatomy of a Class

public class Student {

    // Fields (state)
    String name;
    int rollNo;

    // Method (behaviour)
    void display() {
        System.out.println(name + " - " + rollNo);
    }
}

Class vs File

  • A file may contain multiple classes.
  • Only one may be public, and it must match the file name.
  • Classes are reference types — variables hold references, not values.

Why This Beats a Single main()

  • State is grouped with the behaviour that operates on it.
  • Multiple students can exist independently.
  • Code becomes reusable and testable.
  • The design mirrors the real-world domain.
OOP Thinking

What Is an Object?

Definition

An object is a specific instance of a class — a concrete entity created in memory with its own copy of the class's fields.

Creating an Object

Student s1 = new Student();
s1.name = "Alice";
s1.rollNo = 101;

Student s2 = new Student();
s2.name = "Bob";
s2.rollNo = 102;

s1.display(); // Alice - 101
s2.display(); // Bob - 102

What Happens at new

  1. Memory is allocated on the heap.
  2. Fields are initialized to defaults.
  3. The constructor runs.
  4. A reference to the object is returned.

Reference Semantics

Student a = new Student();
Student b = a;       // b points to same object
b.name = "Zara";
System.out.println(a.name); // Zara

Both variables reference the same object. Changing through one is visible through the other.

OOP Thinking

State, Behaviour, Identity

State

The data an object holds — its fields. State changes over the object's lifetime.

String name;
int rollNo;
double gpa;

"What does this object know?"

Behaviour

The methods an object exposes — what it can do or what can be done to it.

void display() { ... }
void promote() { ... }
double average() { ... }

"What can this object do?"

Identity

What distinguishes one object from another, even if their state is identical. In Java, identity is the object's reference.

Student a = new Student();
Student b = new Student();
a == b // false (different identities)

"Which object is this?"

Worked Example

Two students may share the same name and roll number in a hypothetical dataset, but they are still distinct objects. Identity is not the same as equality of state.

OOP Thinking

Methods as Commands / Actions

Procedural View

In procedural code, functions are the centre of gravity. Data is passed in, transformed, and returned.

double balance = 1000;
balance = deposit(balance, 500);

double deposit(double bal, double amt) {
    return bal + amt;
}

Object-Oriented View

In OOP, the object is the centre of gravity. Methods are commands sent to the object, and the object is responsible for its own state.

BankAccount acc = new BankAccount(1000);
acc.deposit(500);
acc.withdraw(200);
System.out.println(acc.getBalance()); // 1300

The Shift in Thinking

Instead of asking "what function do I call?", ask "which object should handle this, and what message do I send it?" This is the essence of object-oriented design.

Class / Object Declaration — Student, Book, BankAccount

Student

public class Student {
    String name;
    int rollNo;

    void display() {
        System.out.println(name + " - " + rollNo);

State: name, rollNo. Behaviour: display().

Book

public class Book {
    String title;
    String author;
    double price;

    void printDetails() {
        System.out.println(title + " by " + author
            + " — Rs." + price);
    }

BankAccount

public class BankAccount {
    private double balance;

    public void deposit(double amt) {
        if (amt > 0) balance += amt;
    }

    public void withdraw(double amt) {
        if (amt > 0 && amt <= balance) {
            balance -= amt;
        }
    }

    public double getBalance() {
        return balance;
    }
}

Viva Point

Be ready to explain why balance is private and why deposit validates its input. This is encapsulation in practice.

Summary and Checklist

Key Takeaways

  • String is immutable; StringBuilder is mutable.
  • Use equals() for string content, == for references.
  • Wrapper classes let primitives participate in collections.
  • Autoboxing/unboxing is convenient but has a null hazard.
  • Varargs allow variable-length argument lists — one per method, last position.
  • Packages organize code and prevent naming collisions.
  • Access modifiers implement encapsulation.
  • Debugging is a hypothesis-driven process, not guesswork.
  • A class is a blueprint; an object is an instance.
  • State, behaviour, and identity define an object.
